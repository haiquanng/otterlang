# Deployment

```
Browser ──► Vercel (frontend, https://<app>.vercel.app)
              └─ /api/* ──rewrite──► Render (FastAPI, https://otterlang-api.onrender.com)
                                        └─► Supabase Postgres (session pooler)
cron-job.org ──GET /health every 10 min──► Render (keeps the free instance awake)
```

**Why the proxy:** if the browser called Render directly, the refresh cookie would be a third-party cookie. Safari (and soon Chrome) blocks those, so everyone would be signed out on every reload. Through `/api` the browser sees one site, the cookie is first-party, and no CORS is involved.

## 1. Render (backend)
1. Render dashboard → **New → Blueprint** → pick `haiquanng/otterlang`. It reads `render.yaml` (service `otterlang-api`, free plan, root `backend/`).
2. Fill the `sync: false` variables:
   - `DATABASE_URL`: Supabase → Connect → **Session pooler** URI (port 5432), with the database password.
   - `CORS_ORIGINS`: `http://localhost:5173` (only local dev calls the API directly; production goes through the proxy).
   - `JWT_SECRET` is generated by Render. `COOKIE_PATH=/api/auth`, `COOKIE_SECURE=true`, `COOKIE_SAMESITE=lax` come from the blueprint.
3. Deploy, then open `https://<service>.onrender.com/health` and expect `{"status":"ok"}`.
4. If the service URL is not `otterlang-api.onrender.com`, update the destination in `frontend/vercel.json`.

## 2. Database
From your machine, with `backend/.env` pointing at Supabase:
```
cd backend && .venv/bin/python -m scripts.migrate
.venv/bin/python -m scripts.create_user you@example.com --name "You"   # if not created yet
```

## 3. Vercel (frontend)
1. Vercel → **Add New → Project** → import the repo → **Root Directory: `frontend`**. Framework preset Vite (build `npm run build`, output `dist`).
2. Environment variable: `VITE_API_URL=/api` (Production and Preview).
3. Deploy. `vercel.json` handles the `/api` proxy and SPA routes.

## 4. Keep-awake cron
cron-job.org → new job → `GET https://<service>.onrender.com/health` every 10 minutes. Hit Render directly, not through Vercel, so pings do not count against Vercel.

## 5. Check
- Open the Vercel URL on an iPhone (Safari) and on desktop: sign in, reload, still signed in.
- Add a document, learn a word, wait a few seconds: the definition appears in the Library.
- Settings → Server shows Online.

## 6. CI/CD

```
PR ──► CI: lint · types · unit · backend integration (Postgres) · e2e (Playwright)
merge to main ──► Render and Vercel auto-deploy (their own Git triggers)
                  Render build: pip install → migrate → start
```

- **CI** (`.github/workflows/ci.yml`) only runs the jobs for the part of the repo that changed.
- **Deploys** use Render's and Vercel's built-in auto-deploy on `main`; there is no extra gate.
- **Migrations** run in Render's build step (a few seconds, idempotent), so code never starts before its schema exists. A failing migration fails the build and the old version keeps serving.

### Render setting (once)
Your service was created by hand, so set **Build Command** to
`pip install -r requirements.txt && python -m scripts.migrate`.

## Notes
- First request after a long idle can take ~1 minute (Render cold start); the app shows a "waking up" state.
- `SIGNUP_ENABLED=false` until friends are invited; create accounts with `scripts.create_user`.
